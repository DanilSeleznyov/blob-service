# ПОРЯДОК РАЗРАБОТКИ BLOB SERVICE
 
0. Перед началом разработки я определил для себя в общем архитектуру и итоговую форму всего приложения, а также настроил сразу репозиторий для разработки. На этом этапе немного посоветовался с нейронкой, чтобы ничего не пропустить и правильно организовать. Поскольку задача стояла разработать чисто бэкенд-сервис, тестировать решил через postman (p.s.: В конце всё-таки решил доделать небольшой клиент чтоб тестить из терминала, с флагами)

1. Первым делом я начал с создания структуры проекта, отделил внутреннюю логику программы (то что в интёрнал) от энтри-поинтов (то что в cmd), создал все необходимые файлы - гитигнор, докер-игнор, докер-компоуз, докерфайл, также .env.example со списком переменных окружения (у меня всё работает на дефолтах из докер-компоуз, поэтому сам .env себе не создавал). И решил сразу создать все *.go + .proto + *.sql файлы, чтобы сразу видеть фронт работы и все слои программы. 

2. Непосредственно кодинг начал я с докер-файлов, чтобы сразу уже иметь настроенное окружение, и дальше заниматься только логикой самого блоб-сервиса. В докер-компоуз прописал переменные окружения, в докерфайле команды для сборки образа. В папке migrations лежат sql файлы (на данный момент только 1), предназначенные для создания таблицы при старте и накатывания миграций в дальнейшем. Да, сейчас логика "накатывания" версий не реализована в полной мере, поскольку эти sql файлы выполняются только 1 раз, при первой инициализации (тоесть для применения нового файла надо прям полностью пересоздавать таблицу), но фундамент для архитектуры миграций есть. Также на этом этапе прописал конфиг, настроил получения переменных окружения.

3. После настройки всего окружения и базы данных, занялся прото-файлом, прописал там базу для управления блобами (5 методов - create, get, update, delete, list). Ну и сразу скомпиллировал это все в go файлы со структурами и готовыми методами (в процессе перекомпиллировал несколько раз, приходилось править кое-что). Дальше разобрался, как настроить связь с postgres, и закодил функцию NewDB для этого. Дальше ещё какое-то время занимался файлом repository.go - логикой запросов к БД, и обработкой ответов. Почти до конца разработки его правил, чинил выявленные баги. Например, то что сразу не предусмотрел, что метадату (которая у нас в go находится как map[string]string) надо сериализовать и переводить в json и в байтовый срез, в виде которого эти данные хранит БД. И на чтение, соответственно наоборот, десериализовать.

4. Следующим слоем после репо, кодил grpc.go с обработчиками для каждого метода. В обработчике валидируются входящие данные и вызывается соответствующий метод, + обрабатываются ошибки. Когда закончил с обработчиками, ядро программы уже ведь готово, и пошёл кодить сервер, который будет связывать всё воедино. Там он в принципе только подгружает конфиг, создает базу данных с переменными окружения, организовывает структуру в 4 слоя (БД -> репо -> сервер -> gRPC), и вешает слушателя на порт из конфига, который будет принимать запросы и направлять обработчикам. 

5. Уже под конец понял, что неплохо было бы допилить небольшого клиента, чтоб проще всё тестировать, и не быть привязанным к постману. Посоветовался с нейронкой, понял, что лучше всего организовать всё через аргументы ком. строки и систему флагов. По итогу он конечно получился жирнее чем я планировал, там под каждый метод пришлось закодить отдельную функцию обработчик, которая все валидирует и правильно упаковывает перед вызовом внутреннего обработчика блобСервиса, плюс решил ещё реализовать скачивание файла при методе Get с флагом --out, но в целом клиент получился рабочий.

6. Ну по итогу всё получилось как я хотел, можно грузить файлы, перебирать их там, выгружать, удалять, все критичные баги, которые были, я исправил. 

7. Ещё продублирую юзейдж из клиента сюда на всякий случай:

``` blob-service client ```
``` usage: client <command> [flags] ```
``` commands: ```
```   create   upload a file as a new blob ```
```   get      download a blob by id ```
```   list     list blobs with filters ```
```   update   replace a blob (full replace) ```
```   delete   remove a blob by id ```
``` examples: ```
```   client create --file photo.jpg --tags demo,vacation ```
```   client get --id <uuid> --out downloaded.jpg ```
```   client list --name photo --tags demo --limit 10 ```
```   client update --id <uuid> --file photo2.jpg --tags demo ```
```   client delete --id <uuid> ```
``` or (from root directory): ```
```   go run ./cmd/client create --file photo.jpg --tags demo,vacation ```
